# Data model

Capstone deliverable: *"Database schema or data model for applicable services."*

Four databases, one per owning service, with no shared schema and no cross-database join. The
authoritative DDL is the Flyway migration set in each service; this document is the readable view of
it.

| Service | Database | Tables | Migrations (source of truth) |
|---|---|---|---|
| Catalog | `catalog_db` | `cakes` | `catalog-service/src/main/resources/db/migration/V1__create_cakes.sql`, `V2__seed_cakes.sql`, `V3__more_sample_cakes.sql` |
| Order | `order_db` | `basket_items`, `orders`, `order_items` | `order-service/.../V1__create_baskets_and_orders.sql` |
| Rating | `rating_db` | `ratings` | `rating-service/.../V1__create_ratings.sql` |
| Notification | `notification_db` | `notifications` | `notification-service/.../V1__create_notifications.sql` |

Every service also carries Flyway's own `flyway_schema_history`, which is the quickest way to confirm
which migrations ran.

## Conventions that hold everywhere

- **Primary keys are `UUID`, generated by the owning service**, never by the database. No sequences and
  no auto-increment, so a service can build a full aggregate in memory before it writes.
- **Money is `NUMERIC(12,2)`**, read and written as `BigDecimal` at scale 2 `HALF_UP`. No `DOUBLE` or
  `REAL` column exists anywhere in the project.
- **Timestamps are `TIMESTAMPTZ`**, mapped to `java.time.Instant`.
- **Enums are stored as their string name** in a `VARCHAR(20)`, via `@Enumerated(EnumType.STRING)`.
  Ordinal storage is specifically avoided — see the partial index on `notifications` for a case where
  it would silently break a constraint.
- **`ddl-auto: validate`.** Hibernate never creates or alters a table; Flyway owns the schema and
  Hibernate only checks that the entity mapping matches what it finds.

## The one relationship that crosses a service, and why it has no foreign key

`basket_items.cake_id`, `order_items.cake_id`, `ratings.cake_id`, and `notifications.order_id` are
plain `UUID` columns with no `REFERENCES` clause. This is the database-per-service boundary made
literal: the rows they point at live in a different database owned by a different service, so a
foreign key is not merely undesirable, it is impossible.

The consequences are real and accepted:

- A cake can be deleted from `catalog_db` while basket lines still reference it. Nothing breaks,
  because the Order Service snapshots `cake_name` and `unit_price` onto the line at add time and never
  re-reads them.
- The Rating Service will store a rating for any UUID, including one that is not a cake. It does not
  call the Catalog Service to check. That keeps rating throughput independent of catalog availability
  and admits orphan ratings as the trade.
- `notifications.order_id` can name an order that no longer exists in `order_db`.

The only foreign key in the whole system is `order_items.order_id -> orders.id`, and it exists because
both tables are owned by the same service.

## catalog_db

### `cakes`

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `UUID` | PK | |
| `name` | `VARCHAR(150)` | NOT NULL | |
| `description` | `VARCHAR(1000)` | nullable | |
| `category` | `VARCHAR(50)` | NOT NULL | Free-text, not an enum; 9 distinct values in the seed data |
| `price` | `NUMERIC(12,2)` | NOT NULL, `CHECK (price >= 0)` | |
| `available` | `BOOLEAN` | NOT NULL, DEFAULT TRUE | Availability is a flag, not a stock count — inventory is out of scope |
| `image_url` | `VARCHAR(500)` | nullable | Reference only; no image is stored or served by this project |

Indexes: `idx_cakes_category_lower` on `lower(category)`, `idx_cakes_name_lower` on `lower(name)`,
`idx_cakes_price` on `price`. The two `lower(...)` expression indexes exist because the filter API
matches name as a case-insensitive substring and category as case-insensitive equality; without them
those predicates could not use an index at all.

Seed data: `V2` and `V3` together insert **24 cakes across 9 categories**, priced 2.50 to 149.99, with
4 rows deliberately `available = FALSE` so the `409 CAKE_UNAVAILABLE` path is reachable without
editing data. `V1` and `V2` are never modified — Flyway validates checksums on every start, so new
sample data goes into a new version.

## order_db

### `basket_items`

A basket is not a table. There is no `baskets` row and no basket identifier: a basket *is* the set of
`basket_items` sharing a `customer_id`. That is why `GET /api/baskets/{customerId}` answers `200` with
an empty list rather than `404` — there is nothing that could be missing.

| Column | Type | Constraints |
|---|---|---|
| `id` | `UUID` | PK |
| `customer_id` | `VARCHAR(100)` | NOT NULL |
| `cake_id` | `UUID` | NOT NULL, no FK (different database) |
| `cake_name` | `VARCHAR(150)` | NOT NULL — snapshot from the Catalog Service |
| `unit_price` | `NUMERIC(12,2)` | NOT NULL, `CHECK (unit_price >= 0)` — snapshot |
| `quantity` | `INTEGER` | NOT NULL, `CHECK (quantity > 0)` |

`CONSTRAINT uq_basket_customer_cake UNIQUE (customer_id, cake_id)` is load-bearing: it is what makes
adding a cake already in the basket a quantity increment (`200`) rather than a duplicate line (`201`).
Drop it and the same cake appears twice with independent quantities.

`quantity > 0` means "remove" is a `DELETE`, not an update to zero. There is no such thing as a
zero-quantity line.

Index: `idx_basket_items_customer` on `(customer_id)`, backing both the basket read and the checkout
clear.

### `orders`

| Column | Type | Constraints |
|---|---|---|
| `id` | `UUID` | PK |
| `customer_id` | `VARCHAR(100)` | NOT NULL |
| `customer_email` | `VARCHAR(255)` | NOT NULL — stored, but never returned by `GET /api/orders/{orderId}` |
| `total` | `NUMERIC(12,2)` | NOT NULL, `CHECK (total >= 0)` |
| `status` | `VARCHAR(20)` | NOT NULL — `CREATED` or `CONFIRMED` |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |

`total` is written once at checkout from the basket total and read back as-is. It is never re-summed
from `order_items`, so a historical order keeps the price the customer actually agreed to even if an
item row were later touched.

`customer_email` is held back from the order read deliberately: that endpoint is unauthenticated, and
the address is only needed by the `order.completed` event on its way to the Notification Service.

Index: `idx_orders_customer` on `(customer_id)`.

### `order_items`

| Column | Type | Constraints |
|---|---|---|
| `id` | `UUID` | PK |
| `order_id` | `UUID` | NOT NULL, `REFERENCES orders (id) ON DELETE CASCADE` — the only FK in the project |
| `cake_id` | `UUID` | NOT NULL, no FK |
| `cake_name` | `VARCHAR(150)` | NOT NULL — captured at checkout |
| `unit_price` | `NUMERIC(12,2)` | NOT NULL, `CHECK (unit_price >= 0)` — captured at checkout |
| `quantity` | `INTEGER` | NOT NULL, `CHECK (quantity > 0)` |

Checkout copies each `basket_items` row here and then deletes the basket rows, all in one
transaction. `line_total` is **not** a column: it is derived as `unit_price * quantity` for display
only, so it cannot drift from its inputs.

Index: `idx_order_items_order` on `(order_id)`.

## rating_db

### `ratings`

| Column | Type | Constraints |
|---|---|---|
| `id` | `UUID` | PK |
| `cake_id` | `UUID` | NOT NULL, no FK |
| `customer_id` | `VARCHAR(100)` | NOT NULL |
| `score` | `INTEGER` | NOT NULL, `CHECK (score BETWEEN 1 AND 5)` |
| `created_at` | `TIMESTAMPTZ` | NOT NULL |

The `CHECK` is the database-level guarantee that an average can never fall outside 1–5, independent of
the `@Min(1) @Max(5)` bean validation in front of it.

There is **no** unique constraint on `(cake_id, customer_id)`: one customer may rate the same cake
repeatedly and every rating counts. That is a deliberate simplification — deduplicating or replacing a
customer's prior rating is not in the brief.

The average is computed by query, not stored. No `average_rating` column exists, so there is no
denormalized value that can go stale.

Index: `idx_ratings_cake` on `(cake_id)`, backing both the list and the average aggregate.

## notification_db

### `notifications`

One row per delivery **attempt**, not per order. That is why the read endpoint returns an array.

| Column | Type | Constraints |
|---|---|---|
| `id` | `UUID` | PK |
| `order_id` | `UUID` | NOT NULL, no FK |
| `channel` | `VARCHAR(20)` | NOT NULL — `EMAIL` or `IN_APP` |
| `status` | `VARCHAR(20)` | NOT NULL — `SENT` or `FAILED` |
| `attempted_at` | `TIMESTAMPTZ` | NOT NULL |

The interesting constraint:

```sql
CREATE UNIQUE INDEX uq_notifications_order_sent
    ON notifications (order_id) WHERE status = 'SENT';
```

A **partial** unique index. It constrains only the rows where `status = 'SENT'`, so any number of
`FAILED` attempts for one order is fine while a second `SENT` row for the same order is rejected.
That is the database half of "at most one successful confirmation per order"; the listener's pre-send
check is the application half, and both are needed — two listener invocations racing on the same event
can both pass the check, and the index is what stops both inserting.

This index is also why `status` must be stored as a string. It compares against the literal `'SENT'`,
so switching the entity to ordinal enum mapping would leave the index in place and silently
non-functional.

Index: `idx_notifications_order` on `(order_id)`.

## PostgreSQL versus H2

`db/migration/` is PostgreSQL and is the source of truth. Two H2 mirrors exist for running without a
database server:

| Location | Profile | Packaged in the jar? |
|---|---|---|
| `src/main/resources/db/migration/` | default | yes — PostgreSQL |
| `src/main/resources/db/h2/` | `local` | yes |
| `src/test/resources/db/migration-h2/` | `test` | no |

The mirrors are maintained by hand and one difference is not cosmetic: **H2 supports neither partial
nor expression indexes**, so `uq_notifications_order_sent` is replaced by a plain non-unique index on
`(order_id, status)`. The database-level uniqueness guarantee therefore exists **only on PostgreSQL**.
On any H2-backed run — including the verified local run in [`DEMO.md`](DEMO.md) — only the listener's
application-level check protects the invariant. Any test asserting that a duplicate `SENT` row is
rejected has to run against PostgreSQL.

`ddl-auto: validate` catches column drift between the mirrors and the entities, but it does not catch
index or constraint drift. That is checked by reading the two files side by side.
